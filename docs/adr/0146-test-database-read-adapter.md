# 0146 — Explicit, rollback-only test database reads

Date: 2026-10-24. Status: accepted.

A server can host production and test databases together. A hostname or a name containing “test” cannot authorize access. The user's host configuration explicitly lists each `(server, port, database)` with a stable target ID. The list starts empty. Database names allow only ASCII letters, digits and underscore. System database names and the user’s mandatory deny list can never be overridden; a historical deny-list overlap needs an explicit `confirmedTestDatabase: true` on that exact target. Flow grants refer only to these IDs; agents cannot provide connection settings or mutate the configuration through an app tool. The host verifies `DB_NAME()` exactly after connecting, with no fallback to a default database.

Add the runtime dependency **`tedious` 19.2.2**, a widely used pure JavaScript SQL Server TDS driver with bundled TypeScript declarations. Its [official release history](https://github.com/tediousjs/tedious/releases) dates 19.2.2 to 2026-06-21, well beyond the fourteen-day minimum. Installed exact with `npm install --save-exact --before=2026-10-10 tedious@19.2.2 --ignore-scripts`. Its direct connection/request API avoids a second SQL wrapper or connection pool. [Connection options](https://tediousjs.github.io/tedious/api-connection.html) and [streaming request events](https://tediousjs.github.io/tedious/api-request.html) are the implementation references.

Credentials are a narrowly scoped exception to AGENTS rule 2: the host reads only `SQLCMD_TEST_RO_USER` and `SQLCMD_TEST_RO_PASSWORD` from its launch environment, immediately captures/removes them before launching agents, and uses their values for its own SQL connection; no credential goes to a chat, renderer, evidence, log or child CLI environment. Dedicated SQL authentication logins are provisioned by the user/DBA, never the app. The app exposes no provisioning or production operation.

The parser accepts a deliberately limited single SELECT dialect, with approved scalar/aggregate built-ins. It rejects comments, extra statements, DML/DDL, EXEC, INTO, USE, variables, temp names, system schemas, table hints, CTEs/subqueries/set operations, user functions, sequences, remote rowsets and multipart database/server references. Each call uses READ UNCOMMITTED, XACT_ABORT ON, certificate-verified encryption, read-only intent, one dedicated connection, a rollback-only transaction, exact database verification, a thirty-second connection timeout, sixty-second query wall-clock deadline and ninety-five-second overall deadline and bounded streamed output. SQL Server's read-only intent is a routing hint, **not** a permission boundary. Every normal query exit attempts rollback; an aborted/broken session is closed, which rolls back its transaction server-side. No code path commits.

A least-privilege database principal is mandatory. Syntax checks cannot identify cross-database dependencies hidden by views, synonyms, computed columns or modules. The generic template grants only individually reviewed local tables. A user-authorized broader reader role requires auditing every readable view, synonym, computed column and dependency; there are no broad roles, server privileges, production mappings, executable modules, linked-server mappings or guest access to other application databases. See [provisioning and host setup](../test-database-read-only.md).

This is an application capability boundary, not an OS sandbox. An agent with arbitrary shell access under the same OS account may read user files or process state. The SQL principal's server/database permissions provide the independent containment. Mocked driver tests cover transport configuration, exact targets, output bounds, deadline, revocation and rollback; no live database is contacted during implementation or tests.
