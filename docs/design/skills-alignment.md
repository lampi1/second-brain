# Skill alignment for the six roles

The Orchestrator checks for an unresolved product decision when a new job arrives. The role that finds a later decision asks directly. Outside Plan, a clear job starts immediately. A concrete drawback justifies one alternative with a reason. Once the user confirms, the role proceeds within its existing permissions.

## Coverage and defaults

| Role | Default skills | Trigger and evidence |
| --- | --- | --- |
| Orchestrator | work-intake | On new work, check earlier answers. Ask one consequential question through the existing panel. Transfer the selected answer and the task scope to the next role. |
| Strategist | plan-work | Explore alternatives, turn a goal into acceptance criteria, order dependencies and delegate to named owners. Show the plan in its approval panel. |
| Scout | code-investigation | Use primary sources, reproduce a failure read-only and name the first divergent boundary. Cite evidence and separate observations from hypotheses. |
| Artisan | implement-change | Make the smallest testable change. Cover TDD, behavior-preserving refactoring, UI, documentation, diagrams and scoped commits. Return files, checks and before/after evidence for visible changes. |
| Sentinel | code-review, verify-behavior | Review the diff independently. Choose unit, integration or Playwright by risk. Record flaky conditions, failures and retries separately. |
| Herald | draft-update | Prepare a PR or message for its audience, link evidence, distinguish checks run from gaps and obtain approval for the exact external write. |

## Scope and trust

The app resolves only the selected role’s default, linked and explicitly requested skills. Its shared inventory gives existing brain and user overrides precedence over shipped files. The role pack passes its existing content and path checks. A skill grants no tool, model, permission, external send or plan approval. Shipped-default migrations preserve edited fields, user-locked profiles, packs, trials and restored versions.

On a new Strategist assignment, the authenticated Orchestrator may specify the exact `intakeQuestion` from its most recently answered native panel in the current user request. The host consumes that answer once, when it binds the plan. A new direct request expires outstanding intake. The host supplies the question and answer from that chat, and the recipient starts with one visible clarification. Reusing a conversation for a new task resets the interview. Unrelated plans start empty. An MCP form, permission, app-generated night answer or proposed plan cannot supply an intake answer. Three distinct answered interview questions unlock proposal. The user can choose **Basta domande**, including in the intake panel. Agent-relayed text carries no interview credit. Connector forms never receive the Plan stop answer, and night mode keeps its existing policy. Proposal and approval are distinct.

## Acceptance checks

| Scenario | Expected result | Verification |
| --- | --- | --- |
| One intake answer followed by two new answers | The first appears under the plan’s known answers. The second answer alone cannot unlock a proposal; the third can. | ChatManager with a fake engine, actual user panel answers and plan tools. |
| Repeated question, empty input or connector form | No extra interview credit. A second role cannot borrow a different chat’s private decisions. | Strategy tests and authenticated app-control tests. |
| A plan is proposed | Delegation waits for a separate approval; stale approvals still fail. | Existing strategy and approval regression tests. |
| A configured role is upgraded | Shipped defaults update once, while custom skills, text and permissions persist. | Catalog migration tests using a stored profile. |
| Two yes/no questions in one engine request | The engine is asked to submit one question. | Shared question-shape and harness tests. |
| A disputed product choice | The owning role explains one concrete alternative, accepts confirmation and proceeds. | Prompt contract for the real role frames; model compliance requires observation in use. |

The repository branch check runs typecheck, lint, related unit tests, documentation freshness and the publication guard. No live model calls are needed for the deterministic checks.
