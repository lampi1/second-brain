# Correctness review of PR 19 (feat/file-viewer-v1, "file viewer V1")

Verdict: fix needed

Reviewed: `git diff origin/main...HEAD` at 7b4ee9b (main-side `file-view.ts`, `open-path.ts`, `index.ts`, the contract,
the renderer viewer `FileViewer.tsx` + `lib/file-format.ts`, the callers moved off `app:openPath`), against ADR 0068.
The ADR's deliberate choices (any local file, credential files included, no roots allow-list) are taken as intent and
not reported. Security baseline looked at and found holding: `app:readFile` / `app:showInFolder` go through the typed
IPC sender check (main window, main frame only); UNC, `file://host`, `\\?\` and links to shares are refused before
realpath; the read is bounded; highlighted HTML is highlight.js-escaped text passed through DOMPurify (`span` + `class`
only); markdown keeps images off; SVG/HTML are shown as source text, never rendered; nothing is opened or run.

## Findings (by severity)

### 1. Medium: a file link clicked in the questions window opens nothing visible (regression)

- Where: `src/renderer/actions.ts:347-351` (`openFileViewer`), reached from `src/renderer/components/AskContext.tsx:68`
  via `GenUi.tsx:38-40` (`openFile`); the window is `src/renderer/components/QuestionsWindow.tsx:181`
  (`.qwin-backdrop`, `src/renderer/styles/qwin.css:8-10`: `position: fixed; inset: 0; z-index: 38`).
- What goes wrong: before the PR a file chip called `app:openPath`, which opened the file in its own app, visible
  from anywhere. Now it only calls `go({page:'file',…})`. `openFileViewer` closes the `visual` modal only; the
  questions window is not a `ui.modal`, and its visibility (`QuestionsWindow.tsx:65-66`: `on && cur && calm &&
  !dialog`) does not depend on the page, so the file page is mounted under the full-screen backdrop.
- Scenario: "Domande in finestra" on, a chat asks a question whose context names `C:\work\report.md`
  (`AskContext` renders its link chips in the window layout, `RequestPanel.tsx:266`). The user clicks the chip:
  nothing changes on screen. The only way to see the file is to close the window, and Esc / "Rispondi dopo" turns
  answer-later on (`lib/later.ts`): the window stays closed and new questions wait silently.
- Proof (reasoned from code; renderer behaviour, no unit seam): 1) click chip, 2) `AskContext.tsx:68`
  `openFile(l.href, chatId)`, 3) `GenUi.tsx:39` `openFileViewer(href, chatId)`, 4) `actions.ts:349`
  `ui.get().modal==='visual'` is false, nothing is closed, 5) `actions.ts:350` `go()` → `openPage('file', …)`
  changes the page behind, 6) `qwin.shown` unchanged, so the backdrop still covers the viewer. The PR's e2e
  (`questions.spec.ts:50-51`) clicks the chip in a chat tile, not in the window, so it does not cover this.
- Fix: in `openFileViewer`, also hide the questions window while the viewer is up (without turning
  answer-later on; note `parkQuestions()` alone may not hide it with the setting on), or show the viewer as a layer
  above `.qwin-backdrop`; add an e2e click from the window.

### 2. Low: CSV delimiter guessed from text inside quotes, the table shows wrong columns

- Where: `src/renderer/brain/lib/file-format.ts:91-93` (`parseCsv`).
- What goes wrong: the delimiter is chosen by counting `\t`, `;`, `,` in the raw first line, quoted cells included.
  A comma CSV whose header has a quoted cell with two or more semicolons (or tabs) is parsed with `;` (or tab), and
  then quote handling also breaks (a quote no longer starts a cell), so every row is garbled.
- Scenario: `export.csv` = `id,"notes; comments; misc"` / `1,"a; b"`. The default "Tabella" view shows the columns
  `id,"notes` | ` comments` | ` misc"` instead of `id` | `notes; comments; misc`.
- Proof: `test/review/pr-19/csv-delimiter.test.ts` > "a comma CSV whose quoted header cell contains semicolons is
  still split on commas". Command: `npx vitest run --config test/review/pr-19/vitest.config.ts`. Fails on the PR head
  with received `[["id,\"notes"," comments"," misc\""],["1,\"a"," b\""]]`.
- Fix: count delimiter candidates only outside double quotes when scanning the head line (a small quote-aware loop),
  and keep `.csv` → `,` unless the unquoted counts clearly say otherwise.

### 3. Low: "cited line outside the loaded portion" shown wrongly for CR-only files

- Where: `src/renderer/brain/pages/FileViewer.tsx:83` vs `:33`.
- What goes wrong: the PR changed `Code` to split lines on `\r\n?` (a lone CR is a line end), but the
  `lineUnavailable` check still counts lines with `split(/\r?\n/)`. Before the PR both used `\r?\n`.
- Scenario: a file with classic Mac / some tool output line ends `a\rb\rc` opened as `file.txt:3`. `Code` shows three
  lines and highlights line 3, while the status above says "La riga citata non è presente nella parte caricata"
  (1 line counted, 3 > 1).
- Proof (reasoned from code): `FileViewer.tsx:83` evaluates `'a\rb\rc'.split(/\r?\n/).length` = 1 < 3 → status shown;
  `FileViewer.tsx:33-34` yields `['a','b','c']` and line 3 gets `data-l="3"` with the amber background.
- Fix: count lines the same way in both places (e.g. `result.text.split(/\r\n?|\n/).length`, or reuse `Code`'s split).

### 4. Low: files whose stat size is 0 but that have content show one character as the whole file

- Where: `src/main/file-view.ts:31` and `:34`.
- What goes wrong: the read buffer is `min(cap+1, size+1)` from fstat; when fstat says 0 but the file has bytes
  (Linux procfs/sysfs, some FUSE/virtual files), one byte is read and `more` is false (`final.size` 0 is not greater
  than 1), so the viewer shows a single character with no "showing the first N" notice. Reachable since the PR removed
  the roots allow-list (any local path). Not reachable on a normal Windows NTFS file.
- Scenario: an agent's message names `/proc/self/status` (or `/sys/...`) on Linux; the viewer shows `N`.
- Proof: `test/review/pr-19/zero-size-file.test.ts` > "a zero-size procfs file is read past its stat size, or marked
  as cut" (skipped off Linux). Command: `npx vitest run --config test/review/pr-19/vitest.config.ts`. Fails on the PR
  head: `readFileView('/proc/self/status')` returns `{kind:'text', size:0, shown:1, text:'N', more:false}`.
- Fix: allocate `cap+1` (or read in chunks up to `cap+1`) regardless of `opened.size`, so `count` alone decides `more`.
