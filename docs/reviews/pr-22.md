## 1. High: a pruned run comes back as a new v0 run on every restart, so it is counted again each time

- **Where:** `src/main/chats/manager.ts:1580` (`backfillRuns`: `if (r.s.run || owner?.source !== 'catalog') continue;`),
  together with `src/main/chats/manager.ts:333` (`onPrune` deletes `r.s.run`) and `src/main/chats/manager.ts:1609` /
  `src/main/agents/runs.ts:199` (`adopt` returns undefined for a pruned mirror, so the chat loads with no run).
- **What goes wrong:** once a run is folded into the rollups and pruned, its chat no longer has a run. That happens
  through `onPrune` while the app runs, or through `adopt` → `undefined` when chats load. On the next start,
  `backfillRuns` sees a catalog chat with no run and starts a new legacy v0 run for it. If the chat is closed the v0 run
  ends at once at `closedAt`; otherwise it stays open (it counts in `open`, then goes stale after 72 h). The original
  run is already in the `reviewer/3` rollup, so the same chat is now counted twice. When the store is full, the v0 run
  has the oldest end, so the backfill's own `flush()` prunes it straight into the `reviewer/0` rollup. The chat again
  has no run, and the next start does the same thing. The count grows by one per restart, for every catalog chat
  still in chats.json whose run was pruned (up to 60 closed chats plus every open one).
- **Scenario:** the store reaches RUNS_MAX (5000) or RUNS_BYTES. The oldest ended run belongs to an archived chat
  that chats.json still keeps. The user restarts the app three times. The reviewer's ended runs then read 2, 3, 4
  instead of 1.
- **Proof:** test `a chat whose run was pruned into the rollups gets no new backfilled run after a restart (no double
  count)`. It fails with `expected [ 2, 3, 4 ] to deeply equal [ 1, 1, 1 ]`.
- **Fix:** mark the chat as pruned rather than run-less. For example, keep a `runPruned: runId` tombstone in the
  stored chat when `onPrune` or `adopt` drops the mirror, and skip such chats in `backfillRuns`.

## 2. Medium: `turnAt` is set per change to the running state, not per turn, so a report can go to the wrong turn

- **Where:** `src/main/chats/manager.ts:2076` (`if (p.state === 'running' && !r.handoffTurn) r.turnAt ??= Date.now();`)
  and `src/main/chats/manager.ts:1440-1442` (`turnAt` is cleared only when a result arrives).
- **What goes wrong:** the rule is "an ended run takes the report of the turn it ended in, and nothing after". Two
  cases break it, because `turnAt` does not track turns:
  - **(a) A post-end turn writes over an ended run's report.** A turn that ends without a result keeps the old
    `turnAt`, because `??=` keeps it into the next turn. A CLI crash does this: `claude.ts` `finish('error')`. So does
    a clean exit mid-turn. A later turn after the run ended then passes `run.endedAt >= turnAt`, and its run-report
    replaces the real one. That later turn is the Regia writing to a completed chat, which by design does not reopen
    the run.
  - **(b) A queued turn loses its report.** A queued turn starts with no change of state (`claude.ts`: after a result
    with `queued_turn_count > 0` the chat stays `running`), so `turnAt` is undefined for it. If the Regia completes the
    run during that turn, its report is dropped. This is the exact case commit f6bebed means to keep.
- **Proof:**
  - (a) Test `a turn that died without a result does not let a later post-end turn overwrite the ended run's report`.
    It fails with `summary: "dopo la fine"` received, where `"prima"` was expected.
  - (b) Test `a queued turn during which the run is completed still takes its report`. It fails because `report` is
    missing from the completed run.
- **Fix:** clear `r.turnAt` whenever the chat leaves a turn without a result (state `idle`, `error` or `closed`, and
  on session exit). Restart it in `turnEnded` when a queued turn follows. For example, set `r.turnAt = item.at` when
  the chat is still `running` after the result, otherwise delete it.

## 3. Low: `agents:metrics` fails when agent-runs.json cannot be written

- **Where:** `src/main/chats/manager.ts:843` (`runMetrics` calls `this.runs.flush()` without a try).
- **What goes wrong:** `flush()` → `save()` → `writeLocal` throws on any write failure. Examples: on Windows an
  antivirus or indexer holding the file (EPERM on rename), a full disk, or a store in `problem` state after a
  `touch()`. In that last case the chats still hold their mirror runs and `touch()` sets `dirty` anyway. The IPC
  `agents:metrics` then rejects and the metrics view gets an error, although all the data is in memory. Every other
  `flush()` call site (`manager.ts:1245`, `:1589`) and `runSave()` catches and logs.
- **Scenario:** agent-runs.json is locked for a moment. A context-size update marks the store dirty. The user opens
  the agent metrics and gets an error instead of the numbers.
- **Proof:** test `runMetrics still answers from memory when agent-runs.json cannot be written`. It fails with
  `Error: Archivio locale collegato: scrittura rifiutata.`
- **Fix:** in `runMetrics`, call `this.runSave()` (or wrap `flush()` in try/log), then compute from
  `this.runs.list()` / `rolledUp()` as now.
