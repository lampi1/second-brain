# Correctness review: PR 23, file viewer V2 (PDF and paged reading)

Scope: what `feat/file-viewer-v2` (d2bb79e) adds on top of `feat/file-viewer-v1`. V1 is reviewed separately.

## Findings (by severity)

### 1. Medium: PDF page canvases are never released, so memory grows without bound while scrolling a long PDF

- Where: `src/renderer/brain/pages/FileViewer.tsx:83` (canvas sized `width * devicePixelRatio`), `:87` (the
  IntersectionObserver disconnects after the first intersection), `:89` (the only cleanup is on unmount or a width
  change), `:107` (one `PdfPage` per page, all kept mounted).
- What goes wrong: each page is drawn once when it scrolls near and keeps its full-resolution bitmap for as long as the
  viewer is open. Nothing shrinks or clears a canvas when it scrolls away, and `page.cleanup()` is never called.
- Scenario: open a 300-page manual (well under the 32 MB cap) on a 150 % display and scroll to the end. Each US-letter
  page is a 1650 x 2135 canvas, about 14 MB, so about 4 GB of canvas memory sits in the app's own renderer. At 200 % it
  is about 25 MB per page. A 32 MB text PDF can have thousands of pages. The PDF viewer runs in the cockpit's main
  renderer, so running out of canvas memory blanks or crashes the whole app window, not just the viewer.
- Proof (from the code; the repo has no DOM test environment): (1) `PdfPage` mounts for every page (`:107`).
  (2) When a page comes within 800 px, the observer calls `observer.disconnect()` and `draw()` (`:87`), which sets
  `canvas.width/height` to the device-pixel viewport (`:83`) and renders. (3) The observer is gone, so nothing runs
  when the page leaves the viewport. The effect cleanup (`:89`) runs only when `doc`, `n`, `width` or `root` changes,
  or on unmount, and even then it does not reset the canvas. So after scrolling through N pages, N full bitmaps are
  still alive.
- Fix: keep the observer connected. When a page leaves the margin, cancel its task, set `canvas.width = canvas.height
  = 0` and call `page.cleanup()`, then redraw it when it comes back. Or cap the number of drawn pages, for example a
  window of about 10 around the visible ones.

### 2. Medium: a NUL byte after the first page leaves the user stuck on a "binary" error with no pager

- Where: `src/main/file-view.ts:109` (`read.includes(0)` checked on every page), `src/renderer/brain/pages/FileViewer.tsx:178`
  (an error result renders only `<Empty>`, and the pager lives inside `TextBody`), `:170` (the request resets only
  when `ref` changes).
- What goes wrong: V1 checked only the first 1 MB for NUL bytes. V2 checks each page. When a later page contains a NUL,
  Next or End returns `{kind:'unsupported',reason:'binary'}`. `CitedFile` then replaces the whole view with "This file
  does not contain readable text." There is no Start or Previous button any more. Re-opening the same link gives the
  same `reference`, so `ref` is unchanged and the failing request stays. The file can only be read again after
  opening another file.
- Scenario: a Windows log that was preallocated or cut off by a crash or power loss has a run of NULs after 1 MB. The
  first page shows normally. The user clicks Next (or opens a citation in that area) and is stuck.
- Proof: `test/review/pr-23/file-view-paging.test.ts`, test "a page after the first stays readable text when a NUL byte
  appears further into a log". Run `npx vitest run --config test/review/pr-23/vitest.config.ts`. It fails with
  `expected 'unsupported' to be 'text'`.
- Fix: decide "binary" from the head of the file only (as V1 did) and show a later page's NULs as replacement
  characters. Or at least keep the pager (Start, Previous) visible when a page request fails, and reset `request` when
  the same link is opened again.

### 3. Low: AGENTS.md rule 3 broken by the transitive native dependency `@napi-rs/canvas@1.0.11`

- Where: `package-lock.json:865-868` (pulled in by `pdfjs-dist@6.4.299`'s `optionalDependencies`, together with 12
  per-platform native binaries such as `@napi-rs/canvas-win32-x64-msvc@1.0.11`).
- What goes wrong: rule 3 requires packages published at least 14 days before install, via `npm install --save-exact
  --before=<date>`. Running `npm view @napi-rs/canvas time` shows `1.0.11` published `2026-10-10T12:46:50Z`. The PR
  commit is dated 2026-10-18, so the package was 8 days old. With `--before=2026-10-04`, `^1.0.10` would have resolved
  to `1.0.10` (published 2026-10-01), so the lockfile shows that `--before` was not used. `pdfjs-dist@6.4.299` itself is
  fine: it was published 2026-10-03 (15 days earlier), its version is exact, and ADR 0068 has its line. The renderer
  never uses the canvas package, but `npm ci` installs its native `.node` binary on every developer PC.
- Proof: `npm view @napi-rs/canvas time --json | grep 1.0.11` and `git log -1 --format=%cd d2bb79e`.
- Fix: run `npm install --save-exact --before=2026-10-04 pdfjs-dist@6.4.299` to regenerate the lock (it gives
  `@napi-rs/canvas@1.0.10`). Optionally, note in the ADR that the optional native canvas is not needed in the renderer.

### 4. Low: page line numbers overlap because main and the viewer count lines differently

- Where: `src/main/file-view.ts:22` (`newlines` counts `\n` only, used for `firstLine` at `:101`, `:104` and in the
  cited-line path) against `src/renderer/brain/pages/FileViewer.tsx:37` and `:112` (the viewer also starts a new line
  at a lone `\r`).
- What goes wrong: page 1 is numbered by the viewer from 1, splitting on lone `\r`. Every later page gets its
  `firstLine` from main, which counts `\n` only. In a file with lone `\r` (progress redraws from npm, pip, curl or git
  captured to a log), page 2 claims to start at a line number page 1 already showed. On a cited page, the base comes
  from main but the rows are counted by the viewer, so the highlighted row is not the line main found.
- Scenario: a 2.2 MB `build.log` of `step 1/3\r 10%\r 50%\r100%\ndone\n` blocks. The pager says page 1 shows lines
  1-172410, and Next says the following page starts at line 68965.
- Proof: `test/review/pr-23/file-view-paging.test.ts`, test "page 2 starts at the line after the last line the viewer
  numbered on page 1 (lone \r progress lines)". Run the same command as above. It fails with
  `expected 68965 to be 172411`. The test copies the viewer's `lineCount` rule; update it together with the fix.
- Fix: count lines by `\n` only on both sides, as agents' tools cite them. In `Code` and `lineCount`, split on `\n`
  (with an optional preceding `\r`) and keep a lone `\r` inside its row.

## Checked and not a problem

- pdf.js security: `pdfjs-dist@6.4.299` (newer than the CVE-2024-4367 fix in 4.2.67) has no `isEvalSupported` and no
  `new Function`/`eval` in `build/pdf.mjs` or `build/pdf.worker.mjs`. There is no annotation, text or XFA layer
  (`enableXfa:false`) and no scripting manager, so links, forms and JS actions do nothing.
- CSP: `src/renderer/index.html` is unchanged (`script-src 'self'`, no `worker-src`, no `unsafe-eval`). The worker is
  bundled as a same-origin asset (`out/renderer/assets/pdf.worker.min-*.mjs` after `npm run build`). pdf.js gets
  `data`, not a URL, so it makes no network fetch (`connect-src 'self'` is untouched).
- IPC: `app:readFile` keeps the sender check. The new numeric options are sanitized in `index.ts` and clamped to the
  file size in main. A PDF is capped at 32 MB, the `%PDF-` header is checked, and it is re-stat'ed (device, inode,
  realpath, size) around the read. Bytes cross as a `Uint8Array` (structured clone, no base64).
- Lifecycle: the loading task is destroyed on unmount and on file change (`Pdf key={ref}`), also when unmount happens
  before the dynamic import resolves. Render tasks are cancelled and serialized per canvas.
- Paging: a scratch property test (random line lengths, multi-byte characters, lines longer than a page, files of
  2.5-4 MB) checked that following Next from the top joins every byte once, that Previous ends exactly at the page's
  start, that `firstLine` equals the `\n` count + 1, and that a cited line always lands on its page. All passed (not
  committed).
